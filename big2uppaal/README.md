# big2uppaal

Translates a BigraphER model (a `.big` file) into a model for UPPAAL-SMC,
the statistical model checker of UPPAAL, and writes the queries to run on
it. UPPAAL-SMC does not explore every state: it simulates many runs and
reports how often a property held, with a confidence interval.

It reads two kinds of model:

| The `.big` file is | Option | The UPPAAL model is |
|---|---|---|
| a system with probabilistic reaction rules (`begin pbrs`) | `--worlds` | its Markov chain: one process per initial bigraph |
| one bigraph of a compute module in a host site, with no rules | `--system` | power, heat, sound and radio as equations, and the operator's instruments |

This page explains the first with a worked example, and outlines the second
at the end.

## Translate a system with reaction rules

The example is `models/portable-module/src/ae_power.big` in the bigraph-sidc
repository, which has this repository as its `bignix` folder.

That model follows a pulse of power from a GPU to the site operator's meter:
GPU, then PSU, then UPS, then Meter. A `Work` node is a compute burst still
to come. A burst makes one pulse (`Tok`), and the PSU and the UPS each pass
the pulse on or smooth it away. The secret is the number of bursts: two in
the bigraph `sys_s0`, three in `sys_s1`. The predicates `seen1`, `seen2` and
`seen3` hold when the meter has received at least one, two or three pulses.
The question is whether the operator can tell the two worlds apart by
counting pulses.

### Run it

From the top of bigraph-sidc:

```sh
nix-shell bignix/shell.nix
mkdir -p models/portable-module/out
big2uppaal models/portable-module/src/ae_power.big --worlds sys_s0,sys_s1 -o models/portable-module/out/ae_power
```

`--worlds` names the bigraphs to start the rules from. The `init` line of
the file is not used, so the file does not have to be edited to change
world. The command prints:

```
Generated by big2uppaal from ae_power.big. Do not edit.
process sys_s0: the system started from sys_s0, 21 states, 36 transitions
process sys_s1: the system started from sys_s1, 56 states, 126 transitions
One reaction takes one time unit. The queries look at 13 time units.
```

and writes two files:

- `ae_power.xml`: the UPPAAL model.
- `ae_power.q`: the queries, one per world and predicate.

### What the translation does

1. It applies the rules to the initial bigraph in every possible way, as
   `bigrapher full` does, and numbers the bigraphs it reaches. These are the
   states of a Markov chain; state 0 is the initial bigraph.
2. Each world becomes one UPPAAL process, named after its initial bigraph.
   The process keeps the number of the current state in the variable `s`.
3. Once per time unit the process takes one step: it draws the next state
   with the probabilities of the chain. One reaction of the bigraph model is
   one time unit of the UPPAAL model.
4. Each predicate becomes a boolean variable of the process, true while the
   current state satisfies it. So `sys_s0.seen1` in a query means "the meter
   of world `sys_s0` has a pulse".
5. A state to which no rule applies keeps the process where it is and sets
   the variable `ended`.

The start of the process `sys_s0` in `ae_power.xml`:

```c
const int N = 21;  // states: the bigraphs that can be reached. 0 is sys_s0 itself
const int M = 36;  // transitions
// Transition k goes to state TO[k] with probability P[k]. The transitions
// that leave state i are FIRST[i] to FIRST[i+1] - 1.
const int FIRST[N+1] = {0, 1, 3, 4, 7, 10, 13, ...};
const int TO[M] = {1, 2, 3, 4, 4, 5, 6, 7, ...};
const double P[M] = {1.0, 0.5, 0.5, 1.0, 0.5, 0.25, 0.25, 0.25, ...};
```

The table holds 0.25 where the file says `p_psu = 0.5`. In a `pbrs` the
number on a rule is a weight: BigraphER divides it by the sum of the weights
of everything that can react in the same state. When two pulses are on the
move at once, each of their four reactions gets a quarter. The chance that
one pulse ends at the meter is not changed by this.

### Run the queries

`ae_power.q` holds, for each world, one query per predicate and one for the
end of the run:

```
// sys_s0 | seen1
Pr[<=13](<> sys_s0.seen1)
```

This asks for the probability that `seen1` holds at some point in the first
13 time units of a run of world `sys_s0`. Thirteen is one more than the
longest run of either world (three bursts of four reactions each), so every
run has ended by then.

```sh
verifyta -s -q -r 1 -E 0.005 models/portable-module/out/ae_power.xml models/portable-module/out/ae_power.q
```

- `-r 1` fixes the random seed, so the same numbers come out each time.
- `-E 0.005` asks for an interval of plus or minus 0.005 around each
  estimate. The default is 0.05, which is too wide for these probabilities.
- `-s -q` leave out the progress display and the list of options.

`verifyta` prints one result per query, in the order of the file, without
repeating the query. With the values in the file as it is (`p_psu = 0.5`,
`p_ups = 0.2`, both placeholders):

| Query | Runs | 95% interval | Exact |
|---|---|---|---|
| `sys_s0.seen1` | 4490 of 23959 | 0.182 to 0.192 | 0.19 |
| `sys_s0.seen2` | 23 of 2285 | 0.006 to 0.015 | 0.01 |
| `sys_s0.seen3` | 0 of 736 | 0 to 0.005 | 0 |
| `sys_s0.ended` | 736 of 736 | 0.995 to 1 | 1 |
| `sys_s1.seen1` | 8377 of 30854 | 0.267 to 0.277 | 0.271 |
| `sys_s1.seen2` | 119 of 4608 | 0.021 to 0.031 | 0.028 |
| `sys_s1.seen3` | 1 of 912 | 0.00003 to 0.006 | 0.001 |
| `sys_s1.ended` | 736 of 736 | 0.995 to 1 | 1 |

This takes about 20 seconds.

To compare the worlds, compare their rows. The intervals of `seen1` do not
overlap (0.182 to 0.192 against 0.267 to 0.277): the operator sees at least
one pulse more often when there are three bursts, and that is a difference
a meter can measure.

Check the `ended` rows first. If one is below 1, some runs were still going
at the time bound and the other rows are too low: raise `--steps`.

### How this was checked

The "Exact" column was obtained in two ways that do not use UPPAAL:

- PRISM, on the chain that `bigrapher full -p` exports for each world, with
  the property `P=? [ F "seen1" ]` and the same for the other predicates. It
  gives the same numbers of states and transitions as above.
- The tables `FIRST`, `TO` and `P` of the generated `ae_power.xml`, solved
  directly. They give 0.19, 0.01, 0 and 0.271, 0.028, 0.001 to nine digits.

So the generated chain is the right one, and the estimates of UPPAAL agree
with it: every exact value is inside its interval above. The same holds for
a second, larger sample (`-r 2 -E 0.002`, about three minutes), for example
28502 of 149545 runs for `sys_s0.seen1`, an interval of 0.189 to 0.193.

One more check, of `--set`: with `--set p_ups=1.0` the UPS passes every
pulse, and `sys_s0.seen1` should be 1 - 0.5 × 0.5 = 0.75. UPPAAL gives 0.740
to 0.759.

### Options

- `--set NAME=VALUE` replaces a number declared in the file, for example
  `--set p_ups=0.05` for a UPS that smooths more. It can be given several
  times.
- `--steps N` sets the time bound of the queries. It is needed when a run
  can go on for ever (some state can be reached from itself). Otherwise the
  bound is one more than the longest run.
- `--max-states N` gives up when a world has more states than this. The
  default is 10000.

### Limits

- Only a `pbrs` is translated. A `brs` has no probabilities, and an `sbrs`
  has rates, not probabilities.
- Every reachable bigraph is one entry of a table. This suits models with
  up to some thousands of states.
- The UPPAAL model is the chain and nothing more. It has no process for the
  GPU or the UPS, a state is a number, and the name of the rule behind a
  transition is not kept.
- There is no query that compares two worlds directly. UPPAAL has one,
  `Pr[..](<> a) >= Pr[..](<> b)`, but in version 5.0.0 it answered against
  the exact values on this model: it accepted 0.19 >= 0.271, and 0 >= 1,
  with every seed tried. Compare the intervals.

A smaller model of the same kind is in this folder:
`test/models/pulse.big`, with the worlds `one` and `two`.

## Translate a module in a host site

With `--system NAME`, the file holds one bigraph and no rules. The bigraph
is a portable compute module (racks, nodes, GPUs, power supplies, fans,
heat exchangers) composed with a host site and the instruments of the site
operator (a power meter, a temperature probe, an antenna, a microphone, a
network tap). The tool reads who is connected to whom and writes:

- equations for the power drawn, the fan speed and the heat carried away;
- several copies of the module in one model, where copy 0 is the actual run
  and each other copy differs from it in one secret (the model evaluated,
  the benchmark, or one item);
- queries that ask how often the operator's instruments can tell a copy
  from copy 0.

The bigraph has to follow the conventions of this tool: the controls and
their parameters, and connections drawn as pin nodes (`Ein`, `Eout`, `Cin`,
`Cout`, `Dp`, `Obs`). `test/models/mini.big` is a small example:

```sh
big2uppaal bignix/big2uppaal/test/models/mini.big --system sys --report
big2uppaal bignix/big2uppaal/test/models/mini.big --system sys -o /tmp/mini
verifyta -s -q -D 0.1 -r 1 /tmp/mini.xml /tmp/mini.q
```

`--report` prints the views, the links and which of them the operator can
read, and writes nothing. `big2uppaal --help` lists the other options
(`--level`, `--sweep`, `--horizon`, `--only` and so on).

## Build and test

`nix-shell` builds the tool and runs its tests (15) as part of the build.
To build only this package, in the `bignix` folder: `nix-build -A big2uppaal`.

UPPAAL is not free software. It is free of charge for academic use, and
each user needs a licence key from https://uppaal.org, activated once
inside the shell with `verifyta --key <your-key>`. On Apple silicon it runs
under Rosetta. See `nix/uppaal.nix`.
